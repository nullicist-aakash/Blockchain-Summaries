Chapter 7 Lifecycle of Bitcoin - Merkle Trees

In this chapter, we will look at Merkle Hash of a block in Bitcoin. This is computed using data structure known as Merkle Trees. Honestly, this is not required for the philosophy of Blockchain in general, because it is specific to Bitcoin and it is the topic related to mining. You can safely skip this chapter by remembering these lines and come back later when we cover the technical requirements of mining:

Merkle Hash is like the cryptographic hash of payload. It follows all the properties of cryptographic hash functions and we can safely replace it with any other type of hash for blockchain to work. One benefit of Merkle Trees is that it helps in very fast computation of new hash if some data is changed.

Merkle Tree is the requirement for the miners, who introduces new blocks into the system. Users need not, and will not maintain the Merkle Tree on their systems. Once a new block is introduced by miners in the system, they will discard this tree too. So, Merkle Trees only comes into picture when there is active mining going on.

Let’s begin.

We know that the working of cryptographic hash functions have no relation with Blockchain, Blockchain uses cryptographic hash functions. Try to understand the meaning of previous line. It says that cryptographic hash functions have their existence independent of Blockchain, but Blockchain’s existence is strongly tied to cryptographic hash functions. Same thing follows for Merkle Trees and Bitcoin. To fully understand their beautiful properties, we need to understand them outside the context of Bitcoin technology.

Before going to the Merkle Trees and how they work, we need to ask a question: What is the problem statement? As you already saw in previous chapters, this book follows this approach by heart. We first see what we are trying to solve. Only after getting a concrete idea of problem statement, we jump to the solution. But this approach is not that useful in this chapter. Why? Because Merkle Trees are used by miners and we don’t know the requirements of miners yet! So, we will follow other route here. We will specify what properties they have, and in the future chapter of mining, we will use those properties. In this chapter, we will try to get the feeling of how these trees work, what are their computational speed, the working code of their computation. We will discuss other applications of Merkle trees when we discuss Bitcoin - second volume.

7.1 Why we need Merkle Trees

7.1.1 Properties of Merkle Tress

Assume that we are given \(1,000,000\) integers and the size of an integer is \(4\) bytes. In total, we have \(4\times 10^{6}\) bytes. This gives us about \(3.81\) megabytes of data. Say, we compute the cryptographic hash of these numbers. We need to read all numbers, as the output is highly sensitive to each individual bits.

Say we need to update only one integer. What do we need to do to recompute the new hash? After updating the integer, we need to read all \(3.81\) megabytes bytes of data. This may not seem big as the data is only \(3.81\) megabytes, so we use the complexity analysis. When we update some data, even one integer, we need \(O(n)\) time to recompute new hash, where \(n\) is the total number of integers we have. Remember this and make sure you understand this statement by heart.

We use hash functions as black box having all the properties of a cryptographic hash function. Imagine Merkle Tree as a black box too and we claim that the hash output of a Merkle Tree is a valid cryptographic hash. Why is it the case, can be easily verified by reader for all of \(6\) properties when we explain how it is structured. Internally, this is just a data structure that uses a already known cryptographic hash function inside it. This was the case with hashed chains in previous chapter too. The working of hashed chain is independent of any specific hash function used. All that matters is that the function satisfies all the properties of a cryptographic hash function.

So, what benefit does Merkle Trees offer? The major benefit of Merkle trees is that we can update a single integer in our input and the new hash can be recomputed in \(O(\log n)\) time! Make no mistake here. We don’t say that we can compute the hash of \(n\) integers in \(O(\log n)\) time. We said that we can “recompute” the hash in \(O(\log n)\) time. To compute the hash of \(n\) integers from scratch still need \(O(n)\) time, as it should be for every cryptographic hash function. It raises the question: when a change in single bit of data can hugely alter the hash output, how can we change the data and recompute the new hash in \(O(\log n)\) time? Let’s put things into perspective first. We said that we needed the time equivalent to read \(3.81\) mb of data to recompute hash with any cryptographic hash function which is of the order \(O(n)\). With Merkle Trees, we can recompute the hash in time equivalent of about \(21.93\) bytes!!! (In practice, the number will be higher than this due to constant of multiplication in big-O, but we get the idea of scale of things we are looking here).

For the whole discussion, we will assume that number of integers are of power of \(2\), i.e., we can have \(1\) or \(2\) or \(4\) or \(8\) or \(16\) or \(32\) or \(64\) or … integers. How to handle other cases is specific to Bitcoin technology and we will mention it in the end.

7.1.2 Construction of Merkle Trees

Spoiler: If you know about Segment Trees, you already know everything. The specific operation of Merkle Trees is that node stores the hash of the combination of hash of both children. No need to worry if you don’t know about segment trees.

It is assumed that the reader is familiar with the jargon of Binary Trees. Refer to online resources or data structures book for refreshment on Complete Binary Trees and simple node count calculations. Just to be clear, Complete Binary Trees are those trees in which all levels are completely filled.

We assume that our integers are stored in the array, where the size of array is of the form \(2^n\), i.e., array size should be one of \(1,2,4,8,16,32,...\). Denote the size of array as \(N\), so we have the relation \(N=2^n\). We will treat the array elements as leaf nodes of a complete binary tree. Now, you are encouraged to find out the number of nodes on level just above leaf nodes, and above them and so on. Also, you are encouraged to calculate the height of binary tree. The height of tree is the maximum count of nodes that are present on a path from root to leaves. How many nodes are present in the tree (including the leaves)? Here is the answer for above questions:

  1. Number of nodes on level above leaf nodes is \(N/2\) (or \(2^{n-1}\)).
  2. The height of binary tree is \(\log (N) + 1\) (or \(n+1\)).
  3. Number of nodes in the binary tree is \(2N-1\) (or \(2^{n+1}-1\)).

We have our tree with us and the leaf nodes have values as given in the array. What are the values of internal nodes?

That’s where the beauty of Merkle Trees comes into play. Do the following:

  1. Replace the leaf nodes with their cryptographic hash. Remember that we have an array for actual data, so the value of leaf nodes is still with us.
  2. For each node on last second level, “combine” the hash of both of its children (why exactly two children will be there?) and compute the hash of this new combination. Store the resulting hash in current node. For combining, we can simply concatenate hashes of both children.
  3. Repeat the process for last third level and so on till we reach the root.

And we have our beautiful Merkle Tree with us! The hash computed on root is known as Merkle Hash. When we talk about Merkle Hash of data, we mean the above process and report the hash present on the root after these calculations.

Before going further, what is the time required to build this tree? We can see that

  1. Number of hashes we computed are same as the number of nodes in the whole tree.
  2. Time required to compute the hash for an input of size \(O(1)\) is \(O(1)\). Read this line again if you don’t get it in first go.
  3. The storage of hash takes \(O(1)\) space. For instance, SHA-256 hash takes only \(32\) bytes.
  4. If our size of array is \(N\), then the total nodes in tree are \(2N-1\). (Why?)

Combine above points, and we see that we can build our tree in \(O(N)\) time. So far, so good.

7.1.3 Merkle Hash as cryptographic hash

Remember \(6\) properties of cryptographic hash function? Here are they: 1. Input can be of any length. 2. Output is of fixed size. 3. Computation time should be of the order of \(O(n)\) where \(n\) is equivalent to amount to data to read (in bits or bytes or some other multiple). 4. Collision Resistance: No two inputs should give the same output. (Remember how we proved it is not possible theoretically?) 5. Irreversibility: Should not be able to go from hash to input. (Remember something about one-way functions and we saw an example of dice game?) 6. High Entropy: Change in input reflected as huge change in output.

So, can we say that Merkle Hash of inputs is a valid cryptographic hash? Reader is encouraged to think about this. This can be proven via the properties of underlying hash function used by merkle trees and we will not cover them.

7.1.4 Update an integer

Now, we ask our most crucial question: Updating the integer value. Say we change one single integer to new value. How fast can we compute the new Merkle Hash? Reader is again encouraged to see how this can be done in \(O(\log N)\) time from the structure of Merkle Tree.

Here is the intuition: Changing an integer means changing hash of one of the leaf nodes. In the tree, invalid hashes will be the one on the path from left to root.

How many nodes are there on the path from a leaf to root? This is the height of binary tree. What is the height of binary tree with \(N\) leaf nodes? It is \(\log(N) + 1\). So, what do we have with us? We only need to “recompute” these hashes and we will get a valid Merkle Tree in the end. Let’s see the time complexity.

  1. We updated/recalculated \(\log(N) + 1\) hashes.
  2. Computation of a hash takes \(O(1)\) time for \(O(1)\) sized input.

Combine above and we got our result: We can recompute a cryptographic hash (merkle hash to be specific) after changing a single integer in \(O(\log N)\) time.

There is another powerful operation that we can do with this tree and that is: Compute the hash of subarray (consecutive elements) of integers in \(O(\log N)\) time. Say, our numbers are arranged as \([1,4,3,6,5,9,154,56]\). We can use the same tree to compute Merkle Hash of \([3,6,5]\) in \(O(\log N)\) time, where \(N\) is \(8\) here. How this works is out of scope of our discussion and interesting reader can refer Segment Trees about this computation.

7.1.5 Considerations

Here are few points you should keep in mind before applying Merkle Trees to a problem:

  1. Merkle Trees are only used during mining. They are not maintained after a block is placed in the blockchain. The “maintenance” part will become clear in the Merkle Tree computation code of this chapter.
  2. They are as secure as the underlying hash function they use. Remember, that the properties of Merkle Trees are completely dependent on the underlying hash function used. If someone finds a flaw in a specific hash function that is used as cryptographic hash by community, then the structure will no longer remain secure.
  3. The order in which integers are arranged in array matters! The output of hash will drastically change if we swap the location of any two integers and compute the new Merkle Hash. (Why?) Remember this property, as we will use these type of changes in mining.
  4. We are assuming that we only have integers as input. This is no problem for any other data type we want to store, because only the hash of input is stored in the tree and the tree is unaware of underlying input! So, we can replace the integers with transactions in above discussion and the same results will follow.
  5. As the transactions can be as large as \(1\) mb each, we should see what will happen if we use this size in the example at beginning of this chapter (The one with \(1,000,000\) integers). We only compute the hash of one transaction which takes \(1\) mb as input, but subsequent inputs will be \(64\) bytes: We are using double SHA-256 algorithm and combining the children hash with concatenation.
  6. We are assuming that the count of integers is of the power of \(2\) and this is an important assumption. We can eliminate this restriction by filling the remaining entry of leaf nodes with hash of \(0\), a dummy input. For example, say we have \(10\) transactions and we want to compute Merkle Hash. We can use \(0\) as input of remaining \(6\) hash entries of leaf nodes. Bitcoin uses some other technique but this is a valid one too.
  7. To understand the code of Segment Trees in coming section, the reader is expected to know how to represent a complete binary tree using array! Reader can refer to implementation and working of Binary Heaps to understand how this is achieved.

7.2 Segment Trees

7.2.1 Relation with Merkle Trees

If you look up the internet, you will see that segment trees are very useful data structures for competitive programming questions. But if you look into the practical applications of segment trees on internet, you will only example and that is Merkle Trees. Thus, the Merkle and Segment Trees are very closely related. Here is the level of abstractons that are working to build up the Merkle Tree:

  1. Trees - We are specially interested in Complete Binary Trees.
  2. Segment Trees - Complete Binary Trees with some operations to improve some computations. We need to specify the operation to perform and how to combine two children to compute the value of node.
  3. Merkle Trees - Segment Trees with specific operation as cryptographic hash and combination as concatenation of value at children nodes.

We could have used Segment Trees in our discussion but their operations are more abstract. Also, we didn’t discuss how to compute the hash of subarray as hinted in previous section.

7.2.2 Code (Optional)

Note that the following code is for completeness only. You can safely skip if you don’t want to learn segment trees.

The following code is taken from Codeforces. We are representing whole tree as array instead of explicit nodes with two children (technique used in binary heaps too). You will notice that there is an additional operation which we teased about previously: Range query. Range means any contiguous segment of array. We are doing the following operations with segment tree in \(O(\log N)\) time:

  1. Find the sum of any contiguous segment.
  2. Change any array element to any value.

To get a merkle tree, we just have to replace the sum operation with hash operation.

#include <iostream>
#include <vector>

using namespace std;

class SegmentTree
{
    vector<int> tree;
    const int n;

    // return the computed value for the nodes
    static int compute(int a, int b)
    {
        return a + b;
    }

public:
    explicit SegmentTree(vector<int> &arr) : n { (int)arr.size() }, tree{ }
    {
        // Fill Leaf nodes
        tree.resize(2 * n - 1);
        for (int i = 0; i < n; ++i)
            tree[i + arr.size()] = arr[i];

        // Fill internal nodes
        for (auto i = n - 1; i > 0; --i)
            tree[i] = compute(tree[i << 1], tree[i << 1 | 1]);
    }

    // set value at position p
    void modify(int p, int value)
    {
        for (tree[p += n] = value; p > 1; p >>= 1)
            tree[p >> 1] = compute(tree[p], tree[p ^ 1]);
    }

    // sum on interval [l, r)
    int query(int l, int r)
    {
        int res = 0;

        // go up the tree till left and right computations meet
        for (l += n, r += n; l < r; l >>= 1, r >>= 1)
        {
            if (l & 1) res = compute(res, tree[l++]);
            if (r & 1) res = compute(res, tree[--r]);
        }

        // return the result
        return res;
    }
};


int main()
{
    vector<int> arr {5, -3, 6, 1, 0, -4, 11, 6, 2, 7};
    SegmentTree st(arr);

    // Compute the answer for [2, 6]. This means we compute the sum for [2, 7)
    cout << "Sum for range [2, 6] is: " << st.query(2, 7) << endl;

    // Compute the answer for [0, 3]. This means we compute the sum for [0, 4)
    cout << "Sum for range [0, 3] is: " << st.query(0, 4) << endl;

    // Change the element at index 4 to 36
    cout << "Updating the value at index 4 to 36" << endl;
    st.modify(4, 36);

    // Compute the answer for [1, 6]. This means we compute the sum for [1, 7)
    cout << "Sum for range [1, 6] is: " << st.query(1, 7) << endl;
}

Don’t worry about class code. If you focus on the code inside main, you will see how we are using the class API. The example above gives the following output:

Sum for range [2, 6] is: 14
Sum for range [0, 3] is: 9
Updating the value at index 4 to 36
Sum for range [1, 6] is: 47

7.3 Merkle Hash Computation Logic

7.3.1 Pseudo Code

Here, we will mention the algorithm that is used by Bitcoin and use it to verify that our hash computation is correct. Remember that we studied the case when the number of leaf nodes are of power of \(2\), but this is not necessarily true for general case. Also, a user is not required to maintain the merkle tree after the root hash is with us.

Consider an optimization: Do we need to generate and maintain complete hash tree to compute the final root hash? What we mean is, say we have hash of transactions as leaves (assuming power of \(2\) for illustration purposes). Next, we combine their hash one level above the leaves. When we compute hash for all nodes that are parent of leaves, we don’t really need the hash stored in leaves anymore. Similarly, if we have the hash computations on last second level, we don’t need hash of last second level and so on. Going on.., when we have the hash on level \(2\) (assuming root is at level \(0\)), we don’t need hash values of level \(3\). We compute the hashes on level \(1\), and we don’t need hash on level \(2\) anymore. In the end, we compute the hash for root, and we don’t need hash of level \(1\).

Consider what is happening here. Initially, say we had \(N=2^n\) leaf hashes. On level above it, we have \(N/2\) hashes. Above it, we have \(N/4\) hashes and so on. Programmatically, if we store the hash on leaves in an array, that array will be of size \(N\). On first pass, we can make our array the size of \(N/2\) to store the hashes on last second level. We can repeat this till our array has size of \(1\), and that will value will be simply root hash! Here is the pseudo code for the same:

array = [hash of input for each input]  // array size is a power of two
while size of array != 1:
  for (i = 0; i < (size of array) / 2; ++i)
    array[i] = hash(combine(array[2*i], array[2*i+1]))
  
  drop the right half of array making new size exactly half of previous.

Consider what is happening above. Say, we had an array of size \(4\): \([h_0,h_1,h_2,h_3]\). If these hashes represent the hashes on leaf level (level \(2\), assuming root is at level \(0\)), the hashes on level \(1\) are computed as \([h_4,h_5]\) where \(h_4\) is hash of combination of \(h_0\) and \(h_1\). Similarly, \(h_5\) is the hash of combination of \(h_2\) and \(h_3\). Finally, the root hash will be the hash of combination of \(h_4\) and \(h_5\).

Let’s see what happens if we apply above algorithm on \([h_0,h_1,h_2,h_3]\). Since size of array is not \(1\), we enter the while loop. In the for loop, variable \(i\) can only take values of \(0\) and \(1\). For \(i=0\), \(array[0]\) will be updated as hash of \(array[0]\) and \(array[1]\) which contain \(h_0\) and \(h_1\). New array becomes \([h_4,h_1,h_2,h_3]\). Next, for \(i=1\), our array will become \([h_4,h_5,h_2,h_3]\). Then, we drop the second half of array making it \([h_4,h_5]\). Magic! We got our required hashes for level \(1\). Applying the same steps again, we will get our array as \([h_6]\) which is our desired merkle hash.

Now, coming to how Bitcoin handles the general case. If the size of array is even, above algorithm is used. If the size of array becomes odd after iteration of above algorithm, the last element of is appended back again to make the array size even. And the steps are repeated till the size of array becomes \(1\).

Here is the pseudo code:

array = [hash of input for each input]  // array size need not a power of two
while size of array != 1:
  if array size is odd:
    array.append(array.back())
    
  // It is guaranteed that array size is even here
  for (i = 0; i < (size of array) / 2; ++i)
    array[i] = hash(combine(array[2*i], array[2*i+1]))
  
  drop the right half of array making new size exactly half of previous.

7.3.2 C++ Code

Here is the function that takes a vector of hashes as input and generate the Merkle Hash using the same above algorithm. The merkle hash will be stored in index \(0\) of array at the end of execution, and rest of the entries will be deallocated from heap.

// Computes the merkle hash from the given leaf hashes
void merkle_hash(std::vector<uint8_t*>& hashes)
{
    while (hashes.size() != 1)
    {
        // If array size is odd, make it even
        if (hashes.size() % 2 == 1)
        {
            // make a deep copy of last hash so that we can delete it safely without double delete problem
            auto new_elem = new uint8_t[32];
            memcpy(new_elem, hashes.back(), 32);
            hashes.push_back(new_elem);
        }

        for (auto i = 0; i < (hashes.size() / 2); ++i)
        {
            // Concatenate two hashes
            auto concat = new uint8_t[64];
            memcpy(concat, hashes[i * 2], 32);
            memcpy(concat + 32, hashes[i * 2 + 1], 32);

            // Calculate double SHA-256 hash of concatenation
            auto new_hash = double_sha256(concat, 64);
            delete[] concat;

            // delete memory at index i and use current value instead
            delete[] hashes[i];
            hashes[i] = new_hash;
        }

        // Deallocate the other half of vector from heap
        for (auto i = hashes.size() / 2; i < hashes.size(); ++i)
            delete[] hashes[i];

        // resize array
        hashes.resize(hashes.size() / 2);
    }
}

We could have used std::unique_ptr to eliminate unnecessary copies in above code, but it is not used to keep in mind that not everyone is aware of them in C++ and using them increases the complexity for beginners.

        // Read the actual transactions, offset now points to beginning of first transaction
        for (std::uint64_t transaction_index = 0; transaction_index < n_transactions; ++transaction_index)
        {
            auto start_address = block_base + offset;
            std::cout << "\t\tTransaction #" << transaction_index << " offsets: 0x" << HEX(offset, 4) << " to 0x";
            ...
            
            
            // get the length of transaction and compute hash
            auto transaction_len = block_base + offset - start_address;
            hashes.push_back(double_sha256((uint8_t*)(start_address), transaction_len));
        }
        
        // Compute the merkle hash from transactions
        merkle_hash(hashes);
        
        std::cout << "\tMerkle Hash (Computed)   : ";
        for (int j = 31; j >= 0; --j)
            std::cout << HEX(hashes[0][j], 1);

        // deallocate memory of computed hash
        delete[] hashes[0];

        std::cout << std::endl << std::endl;
    }
}

Summary

In this chapter, we covered the details of Merkle Trees. We mentioned that Merkle Trees are useful for miners. We don’t know exactly how, and that’s fine. The importance will come later when we study mining under proof-of-work. As for now, the merkle hash is no different than the ordinary double SHA 256 hash.

We saw that Merkle Tree is a binary tree. We have segment tree over binary tree and Merkle tree is a specific implementation of binary tree. We studied the properties of Merkle trees and how it is computed for transactions. We don’t have anything to discuss the benefits of Merkle Tree as far as our current knowledge is concerned. The practical applications of Merkle Trees will be covered at the end of this volume which is independent of Blockchain or Bitcoin. One application of Merkle Tree is that Apache Cassandra uses Merkle Trees to detect database changes when there are replicas of database spread across the world.
