Bitcoin: A Technical Introduction - Volume I

Chapter 6 Lifecycle of Blockchain - Previous Block Hash

In this chapter, we mark the beginning of our study of “chain” part from Satoshi Nakamoto’s paper. We already covered the block and now, it is time to explore the chain. There are two hashing based data structures that are used in Blockchain/Bitcoin: Hash based chain and Merkle Trees. In current chapter, we will cover the chain part and in next chapter, we will see Merkle Trees. This and coming chapter are going to be exciting as they lay foundation of many properties blockchain possess. These data structures helps us to design some magical systems which are not practical otherwise. So, it is necessary to giver your full attention to the details of their working.

It is important to remember that hash based chain is used in Blockchain while the Merkle Trees fall inside the category of Bitcoin.

Here is the structure of header for reference:

Byte Range Header offset Size (bytes) Meaning Is covered completely till now
8-11 0-3 4 Version Number Yes
12-43 4-35 32 Previous Block Hash No
44-75 36-67 32 Current Merkle Hash No
76-79 68-71 4 Time Yes
80-83 72-75 4 Difficulty No
84-87 76-79 4 Nonce No

As mentioned earlier, blockchain is similar to a linked list. We saw that there is “Previous Block Hash” of \(32\) bytes in the blockchain header. This is double SHA256 hash of header of previous block. The Merkle hash of transactions is stored in the “Current Merkle Hash” field. Basically, transactions are hashed into Merkle Field and the “Previous Block Hash” of next block will just calculate the hash of \(80\) byte header. Instead of calculating the hash of possible \(1\) mb block, we are just calculating the hash of \(80\) bytes to make sure everything is correct. The efficient design! (By the way, we are assuming that Merkle Hash is correctly computed.)

6.1 Hashed Lists

6.1.1 Motivation

It is assumed that the reader already know about singly linked lists.

We already have all the data in disk stored consecutively. When new transactions come, they are going to be stored next to already existing transactions in disk. Since no old transactions are altered, we can simply assume that the storage follows the structure of increasing length arrays instead of linked list. So, why are we using linked lists when we can go with variable length arrays? Why did the developers of Bitcoin store the transactions in linked list type chain instead of array type data structures?

In reality, Bitcoin uses a combination of arrays and hashed lists. We will devote half of this chapter on what these are and in the next half, see what Bitcoin actually implements.

Here are the two fields in a simple linked list structure:

  1. Payload: The actual data stored in node.
  2. Pointer: To the previous element, or next element (Doubly linked lists store both but we are talking about singly list only).

Let’s say we are storing pointer to previous element of list, thus we can go from tail to head but not vice versa. If we change something in the payload of head of linked list, is there any way we can detect something changed? No. Because the payload information is independent of how linked list is working. Now consider what would happen if we have the following fields in the linked list node:

  1. Payload: The actual data stored in node.
  2. Pointer: To the previous element.
  3. Hash: Cryptographic hash signature of contents of previous node. (By content, we mean whole previous node: payload, pointer and hash.)

Say we have the following linked list of \(3\) elements:

Node Address Value Previous Pointer Previous Hash
0xAB451C31 \(10\) - -
0x1AC2B5E3 \(43\) 0xAB451C31 0xABCDEF123456...
0x3C5322F4 \(-5\) 0x1AC2B5E3 0x41CB90AFB213...

Consider what happens if we change anything in the history of above linked list. We have to use one property of cryptographic hash functions: collision resistance. If we change anything in a node, its hash will completely change and we can match it with precomputed hash that is stored in next node! This seems like something we can test right now. Let’s create a linked list, add some elements, change something and see if we can detect a change.

6.1.2 Demo Code

Here is the code which implements above idea: ```{C++} #include #include <unistd.h> #include // for random number generator #include #include “SHA/sha256.h” #define HEX( x, len ) std::setw(2 * len) << std::setfill(‘0’) << std::hex << std::uppercase << (((1ll << (8 * len)) - 1) & (unsigned int)( x )) << std::dec

using namespace std;

struct ListNode { int value; char prev_hash[32]; ListNode* prev; };

struct List { ListNode* tail; char tail_hash[32]; };

// Inserts an integer to the end of linked list void append(List& list, int value) { auto new_node = new ListNode; memset(new_node, 0, sizeof(ListNode));

// Initialise the entries of new tail
new_node->value = value;
new_node->prev = list.tail;
memcpy(new_node->prev_hash, list.tail_hash, 32);

// Calculate hash of new node
SHA256 sha;
sha.update((uint8_t*)new_node, sizeof(ListNode));
auto digest = sha.digest();

// Update the list
list.tail = new_node;
memcpy(list.tail_hash, digest, 32);

// Delete the hash from heap, as it is copied in list
delete[] digest;

}

// Verifies that the list is intact void verify_list(List& list) { if (list.tail == nullptr) { cout << “List is empty” << endl; return; }

auto current = list.tail;
char expected_hash[32];
memcpy(expected_hash, list.tail_hash, 32);

while (current)
{
    // Calculate hash of current node
    SHA256 sha;
    sha.update((uint8_t*)current, sizeof(ListNode));
    auto digest = sha.digest();

    // Print the information about node
    cout << "Node value is: " << current->value << endl;
    cout << "Expected node hash: ";
    for (auto &x: expected_hash)
        cout << HEX(x, 1);
    cout << endl;

    cout << "Computed hash:      ";
    for (int i = 0; i < 32; ++i)
        cout << HEX(digest[i], 1);
    cout << endl;

    // Compare the hash of current node with the hash stored in list
    if (memcmp(digest, expected_hash, 32) != 0)
    {
        cout << "List content is changed!!!" << endl;
        delete[] digest;
        return;
    }

    // Delete the hash from heap, as it is copied in list
    delete[] digest;

    // Move to previous node
    memcpy(expected_hash, current->prev_hash, 32);
    current = current->prev;
}

cout << "We reached the beginning of list!" << endl;

}

int main() { // Create an empty list List list; list.tail = nullptr; memset(list.tail_hash, 0, 32);

// Insert random 5 elements to list

for (int i = 0; i < 5; ++i)
    append(list, (int)mt());

// Verify the list
cout << "Verify initial list: " << endl;
verify_list(list);

// Change the content of some random index
auto current = list.tail->prev->prev;
auto old_val = current->value;
current->value = 0;

// Verify if our program detects the change
cout << endl << endl << "After change the value of third node to 0: " << endl;
verify_list(list);

// Resets the value
current->value = old_val;

// Delete the head of list
auto next_head = list.tail;
while (next_head->prev->prev != nullptr)
    next_head = next_head->prev;

next_head->prev = nullptr;

// Check if our list detects the change!
cout << endl << endl << "After removing the head from the list: " << endl;
verify_list(list);

}


There are two structs: One is `ListNode` which stores the above discussed three parameters. Then, we have `List` which stores the tail pointer and the hash of tail.

Then, we have a function `append` which provides us API to insert integers to the end of list. We use this to encapsulate all the updates in our data structure. Then, we have `verify_list` function which checks if the stored hash of node is actually equal to the calculated hash of node. The reader is encouraged to see the code to verify how this is actually done. Before the start of each iteration of `while` loop, we have the expected hash of value of current node (pointed by `current`) stored in `expected_hash` array. We simply print the status of current node and check if both the hashes match. If there is a mismatch, we simply print that there is a mismatch and return from the function. Otherwise, we go to previous node and repeat the process till we reach head.

In the end, we have the driver code in `main`. We create a list of $5$ numbers that are generated randomly. We don't have to worry about random number generation, as they are handled in built-in `C++` import `<random>`. We verify that the contents are intact. Then, we change the integer value of last third element in list. After running `verify_list`, we should see the error. After that, we changed the list back to initial state and deleted the head from list. We again check if the list is valid, and we should see that there are some problems.

6.1.3 Attacking the list

As you saw above, the hashed linked list is a very powerful data structure. An API can be constructed which hides the details of hashing from outside user. It makes it impossible for users of API to change or delete anything in list after it is inserted. But there is one limitation of above approach. Can you guess why this API scheme is not secure?

Remember that the ledger is distributed across devices and each device receives its copy of every block and transactions! Therefore, it is very easy to access the hash field from data storage and change the contents of it too. Basically anyone can do the following:

  1. Go to a block and change its contents.
  2. Calculate the hash and replace the old hash (original and correct one) with the new hash in next block’s prev_hash field. (Read this again if the statement is not crystal clear).
  3. Since the prev_hash of next block is changed, we need to recalculate the hash of next block and store it in next to next block’s prev_hash.
  4. Repeat above process till we reach tail.

First things first, is there a point of doing above steps? The answer is yes! If we change the hash from past to tail of a target device, we effectively changed the history for that device and the device will fail to recognize any change in the data. This makes it possible to attack any system and take a control over it without much effort.

Coming to practicality of above approach, is it possible to alter the history in fast manner? Yes. All we did in above \(4\) steps is to recalculate the hash and replace the contents of storage. As a hacker, we can do this because the hash calculation is one-way function and it is one of the requirements that hash should be computable in very less amount of time, and is of the order of \(O(n)\).

To summarize, let’s say our mission is to hack a computer and change the records of “append only” ledger. Assume that the task of hacking the device is done and now, we are in full control of storage. We change the transaction we wanted to change. Since calculating hash is very very fast, we recalculate it from our targeted block to the tail of blocks and thus, the device owner will never know if anything is changed at all!

Above process makes it impossible to have our required “append only” ledger which we formulated in the beginning. We can’t go further to specifics of Bitcoin if our Blockchain is not resistant to this type of attack. Fortunately, the theory of computer science can help us here. We will discuss how to solve this problem in next to next chapter when we cover nonce and difficulty.

So, what’s the benefit of hashed chains if they are not tamper-proof? Hashed chains give us the guarantee that we can detect changes as long as whole chain from the altered location is not changed. Nonce will give us guarantee that changing the hash of blocks is not practical! This is part of proof-of-work which we will cover in detail.

By now, you should be able to compute the double \(SHA-256\) of header genesis block on your own and see that it is equal to prev_hash field of next block! Refer to next section for the code on how to do it in C++.

6.2 Blockchain’s prev_hash

6.2.1 Combining arrays and hashed lists

As mentioned in the beginning of this chapter, Bitcoin developers use the combination of arrays and hashed lists to make the content of blockchain tamper-proof. Consider the requirements/observations:

  1. Should be able to append new data. Since the data is appended in permanent storage such as SSD or HDD, we can write new data at the end of file.
  2. Should not be able to change any data once it is there. Hashed chain will help us here.

Here’s a quick question: Is it beneficial to use previous pointer of hashed chains in Bitcoin storage? Think about it before going further. And the answer is: No. There is only one reason that previous pointer exists in singly linked lists and that is: we don’t know in advance how much data is going to be there and RAM storage is not contiguous. The former part is true in our use case, but latter part is not. We are not storing the Bitcoin data in RAM, we are storing it in permanent storage. And in permanent storage, we can append data at the end of file! We can, in practice, assume that our data storage will follow variable-length array (even without any re-allocations that are required in RAM for variable-length arrays).

Also, there is no equivalent of pointer in permanent storage. What do we mean by address in HDD or SSD? Even if there is a concept of address in HDD or SSD, the whole block chain will be present with people across the world. We can’t just assume that all of them will write data in their storage starting from fixed address! We can simply store data one after another, so the core logic of using previous_address is gone from the scope.

Therefore, we can’t use prev_pointer of hashed list, we shouldn’t use use it and there is no need of it. So, we are left with the following fields:

  1. Payload (Data that is application specific, and is not relevant to core working of data structure).
  2. Prev hash (To help us detect if there are any changes).

And nothing more! Once again, our storage is such that we can append data consecutively to the end of previous data.

Time for two questions: Can we move forward in our blockchain? Yes! We did that in previous chapters. Can we move backward? Sadly, no. Remember that payload size of Bitcoin is not fixed! We can’t just go fixed number of bytes earlier in our storage to reach the beginning of previous block.

We can move from current block to next block in storage, and the next block stores the hash of current block. In next section, we will look at code in C++ which also computes the hash of current block.

One final note, remember that we need to compute the hash of \(80\) byte header to get hash of current block. This was mentioned in the beginning of this chapter.

6.2.2 C++ Code

First, we will import header file to compute SHA-256 (Usage explained in previous chapter).

{C++} #include "SHA/SHA256.h"

Then, we define our double hash function:

```{C++} // Computes the double SHA-256 hash of the given data uint8_t* double_sha256(uint8_t* start, int len) { // Calculate hash SHA256 sha1; sha1.update(start, len); uint8_t * digest = sha1.digest();

// Double hash
SHA256 sha2;
sha2.update(digest, 32);
auto digest2 = sha2.digest();

// Remove old digest, as it is not required anymore
delete[] digest;

return digest2;

}


This takes two parameters as input: start location in memory (`start`) and how much bytes to read (`len`). This function returns a heap-allocated array of size $32$ bytes and this should be deallocated manually to avoid memory leak.

At last, we use the above function to compute hash of current block header:

In current chapter, we first saw the properties of hash based chain, how it works. Then, we wrote some code to verify that we can’t alter the contents of any existing node without whole introducing inconsistencies.

Then we saw how we can hack the data structure and indeed change the history! The problem arises because Hash functions are fast to compute and we can’t drop this property. The solution will come when we cover proof-of-work.

At last, we saw how to compute the prev_hash field of block header. We already saw the code of how to verify the contents previously, so we just printed the contents of blockchain and manually calculated the hash. We tabulated the calculated hash and stored prev_hash and saw that they match.

In next chapter, we will look at Merkle Hash and how to compute it.
