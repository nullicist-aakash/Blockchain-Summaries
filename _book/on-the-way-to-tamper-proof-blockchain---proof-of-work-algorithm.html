Chapter 8 On the way to tamper proof blockchain - Proof of Work algorithm

Let’s revise what we have covered. For a currency in which everyone can trust, we needed a system that can’t be changed once some data is there and it is decentralization. Why we need decentralization? To eliminate trust in human entity and trust on well established protocols of cryptography. We know that thousands of transactions happen in the world at any point in time. In Bitcoin, a set of transactions are combined to form a block. As new transactions come into system, new blocks are added. Header contains the hash of transactions (Merkle Hash) so that we can always verify the integrity of transactions a block contains, given that header content is valid. New blocks are added via linked list structure, and this structure takes care of any changes in the entire chain till the latest block (Prev Hash).

So, are we done? Can we take our current ideas and start with Bitcoin? Is this everything we need in blockchain? After all, we can detect if there are any changes in the storage from the beginning of chain to latest block in the chain. And the answer is: not even close! Remember one attack that we covered earlier solely based on speed of computing the hash? Here is the repetition if you forgot about it: You close the software. Someone go in past entries on the storage, change them, recalculate the hash of corresponding block header, recompute the hash of block, change the “prev_hash” entry of just next block, recompute the block hash of next block, change entry in next to next block, and so on till the latest block. You restart the application after some time. Can you detect any changes if you start verifying everything from start? I don’t think so. And why this attack is feasible? Because we can calculate hashes very fast. Can we make hashing algorithm slower to counteract this? Not an option! This defeats the whole purpose of cryptographic functions. Even if we go with this plan, remember that computers are getting fast with the time. Who is to decide how much time a hash function should take?

So, what’s the solution? We know that Bitcoin works, and this book exists. So, there must be a solution. Before going into actual details and missing the point of solution, let’s see another concept in computer science that will be used. Just like cryptographic hash functions, we cover this concept without any context of Blockchain so that we know its existence independent of this technology. After that, we will apply the concept “in abstract manner” to understand how it will help us in preventing above attack. Finally, we go into the actual details of how things are actually implemented. As always, having a working memory model of something is always better than mugging up the implementation and applying it blindly.

There is another set of problems that we are completely ignoring for now. And that is networking! We are currently talking about single system, single user. Once we have clear idea of how everything is handled on one system, we can jump to multiple systems in future chapter to complete our understanding of Blockchain and after that, we can jump into implementation of Bitcoin.

There are other proofs that are used in Blockchain technologies, such as proof-of-Stake in Ethereum. We will cover these in later volumes, as explaining these require more concepts that we don’t require right now.

8.1 Difficult problems in computer science

Study of the “Theory of Computer Science” provides us some insights into how we can solve the problem in hand. There are some problems in computers which are difficult to solve (according to current knowledge of humanity) but are very very fast to verify that given solution to the problem is correct or not. As an example, given a very large positive integer \(n\), can we factor it into two numbers \(x\) and \(y\) such that

  1. \(x,y\in \mathbb{N}\): \(x\) and \(y\) are natural numbers.
  2. \(1<x,y<n\).
  3. \(x\) and \(y\) are prime numbers.
  4. \(x\times y = n\).

It is currently the consensus in humanity that this problem is very very hard to solve “effectively” (note that the wording is loose here, as we are not going into exact details and jargon of computational theory).

But if we are given \(n\), \(x\) and \(y\), we can simply multiply \(x\) and \(y\) to see if their product is equal to \(n\). The RSA algorithm is widely used in industry to enable public key encryption which works on this factoring problem! The world’s trust on secure connection between any two devices rely on this “knowledge” that we can’t factor two integers fast enough.

Before going ahead, we need to see an example why the standard \(O(n)\) algorithm of finding factors from \(1\) to \(n\) will not work. After all, we are claiming that this problem is “very very hard” to solve in practical time limits. Actually, this algorithm is “exponential”, not linear. In computational theory, we use the “number of bits” to represent our length of input, instead of the number represented by those bits! For example, consider the number \((435835)_{10}\). The binary of it is \((110 1010 0110 0111 1011)_2\) which means that the number of bits are \(19\). So, a loop running from \(0\) to \((435835)_{10}\) will take around \(O(2^{19})\) time (Don’t be angry here if you know that this \(O(1)\). What I am trying to say is that the algorithm is exponential - power of \(2\) - in terms of number of bits required to represent the input number). Since the algorithm is exponential, our hope of solving the problem via brute force for large “number of bits” is gone. Here are the time comparison for linear, quadratic and exponential algorithms to keep things in perspective:

\(n\) Time to compute \(f(n)=n\) Time to compute \(f(n)=n^2\) Time to compute \(f(n)=2^n\)
\(10\) \(0.01\) \(\mu s\) \(0.1\) \(\mu s\) \(1\) \(\mu s\)
\(20\) \(0.02\) \(\mu s\) \(0.4\) \(\mu s\) \(1\) \(ms\)
\(30\) \(0.03\) \(\mu s\) \(0.9\) \(\mu s\) \(1\) \(sec\)
\(40\) \(0.04\) \(\mu s\) \(1.6\) \(\mu s\) \(18.3\) \(min\)
\(50\) \(0.05\) \(\mu s\) \(2.5\) \(\mu s\) \(13\) \(days\)
\(100\) \(0.1\) \(\mu s\) \(10\) \(\mu s\) \(4\times 10^{13}\) \(years\)
\(1,000\) \(1\) \(\mu s\) \(1\) \(ms\) -
\(10,000\) \(10\) \(\mu s\) \(100\) \(ms\) -
\(100,000\) \(0.1\) \(ms\) \(10\) \(sec\) -

As you can see, if our bits reach \(100\), the running time reach \(4\times 10^{13}\) \(years\)!! No physical parallelism or speedup of computers can compute this fast in reasonable amount of time. But given two numbers, we have an \(O(n^2)\) algorithm to find product of two numbers, where \(n\) represents the number of bits required to represent both numbers. From above table, we can clearly see the time required to compute the product of two numbers.

Above discussion should have given you a general idea of what we mean by “difficult to solve but easy to verify”. We will use something like this to enforce a “practical” limit (in terms of computational time) on time required to change the entries in block once they are part of Blockchain.

8.2 Working model of Proof-of-work

How can use the above concept of “hard to solve but difficult to verify” in blockchain to prevent the attack presented in the beginning of chapter? Suppose we have a “difficult problem” which will take some time to solve (not the exponential time as present in factorization problem above). For each block, we solve some difficult problem that should “definitely” take “considerable” amount of time to solve by computers. We will cover how Bitcoin solves the problem of increasing speed of computers in a moment, but first, we need to see how solving the difficult problem helps Bitcoin.

8.2.1 Securing Bitcoin by solving a difficult problem

Before adding a new block of new transactions to the end of chain, we (actually miners, but we are not covering them in this chapter) solve a “difficult” problem specific to the block. What do we mean by “difficult” here? Say, solve a problem, which on average, with current computer speeds, take an average of \(5\) minutes to solve (not the actual time limit inside Bitcoin protocol, just used as demonstration to show that there is nothing special in the value chosen in Bitcoin implementation). What do we mean by “specific to the block”? This means that the difficult problem revolves around the transactions inside the block, and the solution will not be valid for any other data. Again, we are talking about problems which are hard to solve but very easy to verify. How does it helps us, if we have such a thing in place?

Consider what will happen in the attack described above if we have something like this in place. Someone goes to history, change the contents, compute new Merkle Hash, go to next block, change the prev_hash entry, … Next, application is restarted and all entries are verified (This is time consuming and doesn’t happen in practice. This will be covered later in detail). We are using the old verification mechanism along with one more additional step:

  • Check if the solution of “difficult” problem is correct or not.

When the application reach the entries that were altered, the “solution” will not match the contents of transactions, as the problem was solved for some other transactions! We detected the changed entries and prevented above attack.

So what’s the benefit? A hacker, proposes the following strategy: Change an entry, recalculate the Merkle Hash, solve the difficult problem, go to next block, update prev_hash entry, go to next block, repeat.

What is the problem in above attack if there are thousands or millions of blocks? Time taken to “update” one block will be \(5\) minutes. To update \(12\) blocks, approach will take \(1\) hour. To update \(1200\) blocks, approach will take \(100\) hours. Seems like that the attack will be successful if there is enough time, right?

NO! Remember that world is actively doing transactions. What is the consequence of this? The number of blocks are also increasing at the rate of \(1\) block per \(5\) minutes, on average. If someone change the entry of last \(10^{th}\) block, that person will need \(50\) minutes to come to block which was last block when attack started. In the meantime, \(10\) new blocks are already entered into the chain! Meaning by? More someone tries to go in past to change some entries, more difficult it is for them to catch up with last block in the entire chain!

This seems like a good solution, as far as we are concerned. And that’s the solution which is implemented inside Bitcoin protocol!

8.2.2 Buying a fast computer to attack the chain

There is a flaw in our implementation. What will happen if a hacker buys a fast computer that can solve problem in \(3\) minutes? In some finite amount of time, hacker will soon reach the latest block in the chain and alter its contents while the new block is being prepared. Once successful, the new block will see the changed block and the prev_hash field will be updated corresponding to new block, which should not be allowed.

So, what’s the solution? As we are only considering a single system right now, this problem can’t be solved. As long as hacker have fast computers than us, the hack can be performed. We will see that we don’t need to care about this attack once we shift to multiple computers sharing the blockchain, as it happen in Bitcoin.
