Internals of Bitcoin

Chapter 3 Structure of a block

3.1 Terminologies

As explained earlier, this book will not tell you why Bitcoin is successful as a technology. Rather, it will tell you the working of each and every byte behind the technology. So, let’s start with the building blocks of the Bitcoin entries.

On top level, we a the concept of a block. A block is a set of transactions. What do we mean by set? A C++ standard container std::set? Mathematical set? What? By set, we just mean a box which can accomodate multiple transactions. How they are stored, is irrelevant to the block.

The first block is known in the community as genesis block. Whenever you see the term genesis block, you should remind yourself of the first block in the blockchain and it doesn’t refer to any other block in entire blockchain.

What is a transaction? A transaction consists of a set of inputs and set of outputs, nothing else. As an example, the record of user \(A\) sending money to user \(B\) counts as a transaction. We don’t bother about structure of a transaction for now but keep in mind that Bitcoin is everything about transaction.

In this chapter, we will cover the structure of a block in bitcoin.

3.2 Theory

3.2.1 Structure of a block

Every block starts with a magic number of \(4\) bytes. What is this magic number? A magic number, in programming, can be explained as a value which have an unexplained meaning in the context and it can be replaced by a named variable to provide more context. Strange? Maybe. It basically says that the number exists there, it serves some purpose, but its intended usage was/is in the mind of programmer writing that and its meaning is not obvious just by looking at it. Some more context is required to see what a magic number is doing there.

Bitcoin have its own magic number: 0xD9B4BEF9. Every block will start with this number, no matter which block you are referring to. Maybe it indicates that a block starts here, maybe you can use it to count how many blocks are there, maybe something else. We don’t know why this specific value is used and it is irrelevant to us as long as working of blockchain is concerned.

But wait, we see that we have F9 BE B4 D9 in the hex output of previous chapter. What is going on? Remember that things are stored in little endian encoding in our computers. Thus, we see the reversed bytes instead of D9 B4 BE F9.

Next, we have the size of block which is stored in \(4\) bytes. If \(100\) is stored in size field, then the size of block will be \(100\) bytes but it will actually take space of \(108\) bytes. These extra \(8\) bytes are there because size specifies how many more bytes are occupied by the block. This is a little optimization so that program doesn’t have to subtract \(8\) from the size field. So, remember, a block of size \(x\) bytes will take \(x+8\) bytes in storage and size field will store \(x\) as the size of block.

What is the maximum size a block can take? For \(4\) bytes, we have \(2^{32}\) bytes which mean, theoretically, we can have blocks as large as \(4\)GB! But, Satoshi Nakamoto had other plans and he silently introduced the limit as \(1\)mb. Refer Block size limit controversy for more details.

Next, we have block header of \(80\) bytes. We will explain it in next section.

Next, we have a field of \(1\) byte, which helps us in determination of the number of transactions. This is half truth, but will be explored in next chapter. Don’t say that number of transactions are stored in this \(1\) byte.

After that, we have the transaction data which will be explored in later chapters.

3.2.2 Structure of block header

In above section, we saw that we have a block header of \(80\) bytes. What is the meaning of header? Why is it used? A header is used to identify some properties about the payload. For example, header of a song file may contain information about artist name, song name, the size of song in bytes, etc. Similarly, we need some information about payload before exploring its contents. What is the payload here? It is the set of transactions that we talked about earlier. Remember, a block acts as a bucket of transactions, nothing else.

The first field in header is of size \(4\) bytes, and is known as version. The genesis block had version \(1\) and as of now, there are \(4\) versions of bitcoin. What is a version or what does it specify? It can be thought of as a message which specifies how the things are placed in the block. The structure of block header which we are going to study corresponds to version \(1\) and it can be different for different versions. The version number helps us programmatically take care of various changes in the rules of data storage/updations of blockchain under single implementation and make code compatible across versions. Or, it helps us split the code in if-else statements to handle different type of blocks.

Next field is of \(32\) bytes and is known as previous block hash field. Since it is assumed you know basics of Bitcoin, we will not go into what a hash is. We will just mention that it is double SHA-\(256\) hash of previous block. Wait.. double hash? Why a double hash? The answer is: We don’t know why Satoshi Nakamoto made this decision and there are many conjectures over this. We simply accept this and move on.

What about the previous hash of genesis block? This is hardcoded as 0x0...0 and this is the only block which has previous block hash set as all zeros.

Next field is also of \(32\) bytes and is merkle hash. What is used to calculate this? This will be discussed later in current chapter. But remember one thing, the value of current hash is also double SHA-\(256\) hash of input.

Next field is the time stamp and is stored in \(4\) bytes. There are two category of questions that can arise for this field: how we are storing time in \(4\) bytes (only) and what does it represent.

We are storing the Unix epoch time. What is it? This is widely used date-time unit in computing and it specifies the number of seconds elapsed since 00:00:00 UTC on 1 Jan, 1970. As a fact, the Unix epoch value \(1000000000\) corresponds to 9 September 2001, 01:46:40 UTC. It was celebrated in Copenhagen, Denmark held by the Danish UNIX User Group at 03:46:40 local time.

What does it represent? It specifies the time miner started hashing current block (time as per the system time of miner). Who is miner? We will cover it in later chapters.

Next \(4\) bytes are difficulty and next \(4\) bytes are nonce. What are they? Again, we will cover them in later chapters.

3.2.3 Calculation of current hash

Note one thing: Hash of block is not equal to its Merkle hash. Hash of block is defined as the hash of header. Header have one field which stores the merkle hash. How Merkle hash is computed is covered when we cover the structure of payload. So, we have following relations:

  • Previous hash entry in block number \(i\) = SHA256(SHA256(header of block number (i - 1))).
  • Previous hash entry in block number \(0\) = Hard coded as all \(00\).
  • Merkle hash entry in block number \(i\) = Explained in later chapters.

You should note that current block hash is not stored anywhere in current block.

3.3 Reading Genesis block Header

  1. We see that initial \(4\) bytes match F9 BE B4 D9, which corresponds to little endian of 0xD9B4BEF9. This is a match.
  2. Next \(4\) bytes read as 1D 01 00 00, which corresponds to little endian of 0x0000011D. This implies that block is spanning in more \(285\) bytes. This makes genesis block have storage space of \(285+8=293\) bytes. This means that first block is stored in offset \(0\)-\(292\) and next block starts at offset \(293\). We can confirm it by going to hexadecimal index 0x125 (which is equivalent to decimal of \(293\)) and reading the magic number. This process can be repeated to see that third block starts at hex offset 0x205 and so on..
  3. Next \(4\) bytes corresponds to version number which is specified as 01 00 00 00 which is little endian equivalent to \(1\).
  4. Next \(32\) bytes specify the previous block hash. This is specified as 0x00 repeated \(32\) times till hex index 0x2C.
  5. Next \(32\) bytes are 3B A3 ED FD 7A 7B 12 B2 7A C7 2C 3E 67 76 8F 61 7F C8 1B C3 88 8A 51 32 3A 9F B8 AA 4B 1E 5E 4A which is the little endian of 0x4A5E1E4BAAB89F3A32518A88C31BC87F618F76673E2CC77AB2127B7AFDEDA33B.
  6. Next \(4\) bytes refers to time. The value is 29 AB 5F 49 which is little endian of 0x495FAB29. Putting this value in online time converter gives the time as GMT: Saturday, January 3, 2009 6:15:05 PM.
  7. Next \(4\) bytes specify the nonce which is 0x1D00FFFF (after converting to big endian) - \(486604799\) in decimal.
  8. Next \(4\) bytes specify the difficulty as 0x7C2BAC1D (after converting to big endian) - \(2083236893\) in decimal.

3.4 C++ code to read the data

3.4.1 Complete Code

Here, we present the C++ code to show information about initial 3 blocks of bitcoin. The genesis block have index of \(0\).

#include <iostream>
#include <fstream>
#include <algorithm>
#include <string>
#define HEX( x, len ) std::setw(2 * len) << std::setfill('0') << std::hex << std::uppercase << (((1ll << (8 * len)) - 1) & (unsigned int)( x )) << std::dec

// Returns the file contents as C++ string
std::string get_file_contents(const char *filename)
{
    std::ifstream in(filename, std::ios::in | std::ios::binary);
    if (!in)
    {
        std::cerr << "Error in opening file" << std::endl;
        throw errno;
    }

    std::string contents;

    // Allocate required memory in heap for string
    in.seekg(0, std::ios::end);
    contents.resize(in.tellg());

    // Copy contents from file to string
    in.seekg(0, std::ios::beg);
    in.read(&contents[0], (int)contents.size());

    // return the string
    return contents;
}

struct BlockHeader
{
    std::uint32_t version_number;
    std::uint8_t prev_hash[32];
    std::uint8_t merkle_hash[32];
    std::uint32_t time;
    std::uint32_t difficulty;
    std::uint32_t nonce;
};

struct Block
{
    std::uint32_t magic_number{};
    std::uint32_t block_size{};
    BlockHeader header{};
};

int main()
{
    const char* FILE_PATH = "<file path here>";
    auto contents = get_file_contents(FILE_PATH);
    std::uint32_t offset = 0;
    for (int i = 0; i < 3; ++i)
    {
        std::cout << "Information about block #" << i << std::endl;

        // create a block
        Block block;

        // copy initial 88 bytes from contents
        memcpy(&block, contents.c_str() + offset, 88);

        // make offset point to next block
        offset += block.block_size + 8;

        // Print current block information

        std::cout << "Magic Number: " << HEX(block.magic_number, 4) << std::endl;
        std::cout << "Blockchain Size: " << block.block_size << std::endl;
        std::cout << "Header Info: " << std::endl;
        std::cout << "\tVersion Number          : " << block.header.version_number << std::endl;
        std::cout << "\tPrevious Hash           : ";
        for (int j = 31; j >= 0; --j)
            std::cout << HEX(block.header.prev_hash[j], 1);
        std::cout << std::endl << "\tMerkle Hash (Stored)    : ";
        for (int j = 31; j >= 0; --j)
            std::cout << HEX(block.header.merkle_hash[j], 1);

        std::cout << std::endl << "\tTime of Block Creation  : ";
        std::time_t temp = block.header.time;
        std::cout << std::put_time(std::gmtime(&temp), "%Y-%m-%d %I:%M:%S %p") << std::endl;
        std::cout << "\tDifficulty              : " << HEX(block.header.difficulty, 4) << std::endl;
        std::cout << "\tNonce                   : " << block.header.nonce << std::endl;
    }
}

3.4.2 Working

You can see that we have two structs in above code: BlockHeader and Block. BlockHeader consumes \(80\) bytes of space in memory, and it is enforced by choosing the data types of appropriate size so that no padding is there. We have Block with magic number and size as \(4\) bytes each, and block header just after them. Overall, we have no padding in the struct and blocks can be placed consecutively without wasting space. This allows us to use memcpy to copy bytes directly to struct without manually copying the bytes for individual fields.

Inside the main, we first read the file contents as binary file into a string. Then, we are printing the information about first \(3\) blocks of bitcoin. We first copy \(88\) bytes from source file to a block, which completely fills all the fields of above block. Then, we print the information about them by iterating over each field, so there is nothing new here. One thing to note is that we are printing the hash in reverse order, and it is because we don’t have 256-bit data type in C++. We are manually printing it in big-endian format.

After printing information about block, we update our offset variable by 8 + block size to make it point to next block.
