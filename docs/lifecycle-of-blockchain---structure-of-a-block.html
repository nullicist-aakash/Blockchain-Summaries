Bitcoin: A Technical Introduction - Volume I

Chapter 4 Lifecycle of Blockchain - Structure of a block

This chapter marks the beginning of our journey into the world of Bitcoin. As already discussed in last chapter, we know the difference between Bitcoin and Blockchain. We also mentioned that this volume is all about the Blockchain, next volume is going to be about individual transactions of Bitcoin. Let’s get started!

Blockchain-type technology was first discussed in a dissertation of 1982 by David Chaum: “Computer Systems Established, Maintained, and Trusted by Mutually Suspicious Groups.” There are few attempts after it to implement the technology, but the first decentralized Blockchain was conceptualized in 2008, by Satoshi Nakamoto. Satoshi used “block” and “chain” separately in the 2008 paper. This means something. This means that we have to study two things to actually understand the blockchain.

There are few aspects of blockchain as a data structure:

  • Add new data at the end - Required.
  • Change existing entries - Should not be allowed.
  • Delete existing entries - Should not be allowed.
  • Iterate over data - Required.

We don’t have any update query. We need some type of search query, but that will be taken care in volume 2. What data structure best fits the above requirements if thought as an API question? Linked Lists. In Blockchain, instead of nodes, we say blocks. In place of pointer to next or previous element, we say chain. Thus, the name: Blockchain.

In this chapter, we will see how the block header is structured. We will see that a block is splitted into four parts: \(8\) byte pre-header, \(80\) byte header, number of transactions and actual transactions. There are some concepts such as difficulty, hash, nonce which will be covered later in detail. These are just mentioned in these initial chapters and where they are stored. Their complete details will come in future.

4.1 Terminologies

On top level, we see the concept of a block. A block is a set of transactions. What do we mean by set? A C++ standard container std::set? Mathematical set? What? By set, we just mean a box which can accommodate multiple transactions. How they are stored, is irrelevant to the block.

The first block is known in the community as genesis block. Whenever we see the term genesis block, we should remind ourselves of the first block in the blockchain and it doesn’t refer to any other block in entire blockchain.

What is a transaction? A transaction is an entry in ledger. As an example, the record of user \(A\) sending money to user \(B\) counts as a transaction. We don’t bother about structure of a transaction for now but keep in mind that Bitcoin is nothing without proper transaction management.

How they fit the big picture? Many transactions are generated in Bitcoin in the world per unit of time. As per the records, it is about \(250\)k to \(400\)k transactions per day. There is no limit on number of transactions we can have, it is just the summary of what is actually happening. We collect few transactions and store them in a block. Nothing else. Who stores them? Who decides what block should have what transactions? We will discuss them in coming chapters.

In this chapter, we will cover the structure of a block. How new blocks are added, is discussed in coming chapters.

4.2 Theory

4.2.1 Structure of a block

Every block starts with a magic number of \(4\) bytes. What is this magic number? A magic number, in programming, can be explained as a value which have an unexplained meaning and it can be replaced by a named variable to provide more context. Strange? Maybe. It basically says that the number exists there, it serves some purpose, but its intended usage was/is in the mind of programmer writing that and its meaning is not obvious just by looking at it. Some more context is required to see what a magic number is doing there.

Bitcoin have its own magic number: 0xD9B4BEF9. Every block will start with this number, no matter which block we are referring to. Maybe it indicates that a block starts here, maybe we can use its occurrence to count how many blocks are there in blockchain, maybe something else. We don’t know why this specific value is used and it is irrelevant to us as long as working of blockchain is concerned.

But wait, we see that we have F9 BE B4 D9 in the hex output above. What is going on? Remember that things are stored in little endian encoding in our computers. Thus, we see the reversed bytes instead of D9 B4 BE F9.

Next, we have the size of block which is stored in \(4\) bytes. If \(100\) is stored in size field, then the size of block will be \(100\) bytes but it will actually take space of \(108\) bytes. These extra \(8\) bytes are there because size specifies how many “more” bytes are occupied by the block. This is a little optimization so that program doesn’t have to subtract \(8\) from the size field. So, remember, a block of size \(x\) bytes will take \(x+8\) bytes in storage and size field will store \(x\) as the size of block. We can see in the code at the end how this helps us in writing clean code without extra steps.

What is the maximum size a block can take? For \(4\) bytes, we have \(2^{32}\) bytes which mean, theoretically, we can have blocks as large as \(4\)GB! But, Satoshi Nakamoto had other plans and Satoshi silently introduced the limit as \(1\)mb. Refer “Block size limit controversy” on the internet for more details.

What is the size of genesis block? If we see next \(4\) bytes, we see 1D 01 00 00. Converting to big endian, we get 00 00 01 1D, which is equivalent to \(285\) in decimal. So, our genesis block is of \(285\) bytes, but takes \(285+8=293\) bytes in storage. Interesting… Can we verify it? Yes. We know that blocks are placed one after another. So, after initial \(293\) bytes, we should be able to see the most popular version number: F9 BE B4 D9 (little endian, what is actually stored). Let’s check. Initial 293 bytes for genesis block means genesis block takes the byte range \(0\)-\(292\). This means next block starts at index \(293\). \(293\) in hexadecimal means 0x125. Going to the row having prefix 0x00000120, we see that 0x120th byte is AC. Going on, we see 0x121th byte is 00, …, we see the 0x125th byte is F9. Reading three more bytes and we see our pattern in byte range 0x125 - 0x128: F9 BE B4 D9. We can play this game for next block and you are encouraged to perform the calculations on your own. You should see that next block starts at hex offset 0x204.

Next, we have block header of \(80\) bytes. We will explain it in next section.

Next, we have payload. What is this? In context of any header-data based structure, metadata refers to the header while payload refers to the data. In payload, we have two things: The number of transactions, and transactions themselves. All the transactions of a particular block are stored here. Remember one thing: we will treat transactions as black box. We will see how multiple “transaction boxes” are placed, not the actual content of “boxes”. Content of these “boxes” is the core interest of volume 2.

4.2.2 Structure of block header

In above section, we saw that we have a block header of \(80\) bytes. What is the meaning of header? Why is it used? A header is used to identify some properties about the payload. For example, header of a song file may contain information about artist name, song name, the size of song in bytes, etc. Similarly, we need some information about payload before exploring its contents. What is the payload here? It is the set of transactions that we talked about earlier. Remember, a block acts as a bucket of transactions, nothing else.

The first field in header is of size \(4\) bytes, and is known as version. The genesis block had version \(1\) and as of now, there are \(4\) versions of Bitcoin (source - Block Versions). What is a version or what does it specify? It can be thought of as a message which specifies how the things are placed in the block. The structure of block header which we are going to study corresponds to version \(1\) and it can be different for different versions. The version number helps us programmatically take care of various changes in the rules of data storage of blockchain under single implementation and make code compatible across versions. Or, it helps us split the code in if-else statements to handle different type of blocks.

Next field is of \(32\) bytes and is known as previous block hash field. What is this? This can be thought of as the “previous pointer” in our linked list analogy. But this does more than that. This makes sure that no data is changed in previous block! We will not go into exactly how a hash is calculated and the proof of its properties, because that requires a strong mathematical background and that is not relevant to the working of blockchain. We will just mention that it is double SHA-\(256\) hash of previous block. Wait.. double hash? Why a double hash? Why not single SHA-256 hash? The answer is: We don’t know why Satoshi Nakamoto made this decision and there are many conjectures over this. We simply accept this and move on. We will study this in more detail in coming chapters.

As we know, all entries should be valid for every block in the system. For new blocks, the “previous hash” field is well defined and we can compute it. But what about the previous hash of genesis block? This is hardcoded as 0x0...0 and this is the only block which has previous block hash set as all zeros.

Next field is also of \(32\) bytes and is merkle hash. We will cover how to compute this in next chapter. But remember one thing, the value of current hash is also double SHA-\(256\) hash of input. This is basically a “proof” that “payload” is what it claims.

Next field is the time stamp and is stored in \(4\) bytes. There are two category of questions that can arise for this field: how we are storing time in \(4\) bytes (only) and what does it represent.

We are storing the Unix epoch time. What is it? This is widely used date-time unit in computing and it specifies the number of seconds elapsed since 00:00:00 UTC on 1 Jan, 1970. As a fact, the Unix epoch value \(1000000000\) corresponds to 9 September 2001, 01:46:40 UTC. It was celebrated in Copenhagen, Denmark held by the Danish UNIX User Group at 03:46:40 local time.

What does it represent? It specifies the time miner started hashing current block (time as per the system time of miner). Who is miner? Miner is responsible to add new blocks in the system. We will cover more about them in later chapters.

Next \(4\) bytes are difficulty and next \(4\) bytes are nonce. What are they? They are used by miners and are the proof that block is a “valid” block. Don’t worry about them for now. We will cover them later in full glory.

4.2.3 Number of transactions

Developers of Bitcoin are very intelligent. They use a very beautiful trick to store the number of transactions. More generally, they use different type of “integer” to store the count of anything in Bitcoin. They use what is known as “variable integer”. So, how does this integer work? This integer can store as long as \(8\) byte number and as low as \(1\) byte number. How?

Here is the scheme: For every number between \(0\) and \(252\) (both included), use \(1\) byte for storage. If the byte is \(253\), it means that the integer value is stored in next \(2\) bytes. If the byte is \(254\), it means that the integer value is stored in next \(4\) bytes. And lastly, if the byte is \(255\), it means that the integer value is stored in next \(8\) bytes!

Sounds complicated? Here is the pseudo code for this scheme:

x = next byte;
if (x >= 0 and x <= 252)
  set y = x
else if x is 253:
  set y = two bytes after x
else if x is 254:
  set y = 4 bytes after x
else if x is 255:
  set y = 8 bytes after x

return y as the integer value

So, are we using \(3\) bytes to store \(2\) byte number? Yes. Are we using \(9\) bytes to store \(8\) byte number? Yes. Are we using \(2\) bytes to store \(1\) byte number? NO! It depends. If the number is less than \(253\), then we are only using \(1\) byte. Here is the table summary for the size:

Range Value of First byte Extra bytes to get number Total size (in bytes)
\(0\) to \(252\) Number - \(1\)
\(253\) to \(2^{16}-1\) \(253\) \(2\) \(3\)
\(2^{16}\) to \(2^{32}-1\) \(254\) \(4\) \(5\)
\(2^{32}\) to \(2^{64}-1\) \(255\) \(8\) \(9\)

Here are some examples. Say, we want to store \(200\). We have to follow this scheme:

  1. Convert \((200)_{10}\) (which means that the number is in decimal) to hexadecimal: \((C8)_{16}\) or 0xC8.
  2. We see that given number is less than \(253\). Thus, this will be stored in \(1\) byte.
  3. What is little endian of C8? It is the same number! So, we will just store C8 in storage.

What if we want to store \(35467\)? We have to follow the following steps: 1. Convert \((35467)_{10}\) to hexadecimal: \((8A8B)_{16}\) or 0x8A8B. 2. We see that given number actually require \(2\) bytes to be represented. So, we have to go with scheme of \(3\) bytes and store FD (hexadecimal of \(253\)) in first byte. 3. What is the little endian of 8A 8B? It is 8B 8A. So, we will store FD 8B 8A in storage.

Let’s cover a corner case. What if we have to store \(254\)? 1. Convert \((254)_{10}\) to hexadecimal: \((FE)_{16}\) or 0xFE. 2. We see that given number actually require \(1\) byte to be represented but it is more than \(252\). So, we we have to with scheme of \(3\) bytes. 3. Before converting to little endian, we have to represent FE in \(2\) bytes: 00 FE. Little endian of this becomes: FE 00. Thus, we store \(254\) as: FD FE 00.

Let’s see what genesis block stores for this value. Going to byte offset \((88)_{10}\) or 0x58, we see the entry as 0x01. So, the genesis block have only one transaction. This is lame… we can’t verify what we just studied. To verify, there are two ways: Either check the internet about what we studied or find a block having some interesting size in the code! Just iterate over blocks (in code) till you find a block with more than \(252\) transactions. Or, you can go to structure of transactions mentioned next and apply these concepts whenever you encounter a “variable integer”.

4.2.4 Transactions

After number of transactions, we have those many number of transactions placed one after another. As promised, we will treat them as black box. One thing that we should know is that transaction can have any size. So, if we treat transactions as black box, how we can predict the size of them? Good question. Here’s when we actually need to go into structure of a transaction. We will just mention what each field is, but this will be covered in great detail in next volume. Ready?

  • First, we have \(4\) byte version number.
  • Second, we have number of “inputs” to transaction stored in “variable integer”. So, this field can be as low as \(1\) byte or as long as \(9\) bytes. Next, we will have corresponding input structures. For each input:
    • We have \(32\) byte of “previous transaction hash.
    • We have \(4\) byte of “output index”.
    • We have “variable integer” bytes for “signature script”, which store how many bytes “signature script” will take next.
    • We have the actual “signature script”, having length specified in previous field.
    • We have \(4\) byte sequence number.
  • Then, we have number of “outputs” to transaction stored in “variable integer”. So, this field can also be as low as \(1\) byte or as long as \(9\) bytes. Next, we will have corresponding output structures. For each output:
    • We have \(8\) bytes for number of “Satoshis”. This is the unit of measurement of Bitcoin inside Bitcoin code. And people say programmers have no sense of humour.
    • We have “variable integer” bytes for length of “public key script”, which is stored next.
    • We have the actual “script”, whose length was specified in previous field.
  • Then we have a “lock time” of \(4\) bytes.

Able to grasp everything? Don’t worry if you are unable to understand meaning of any field. We just need to see the bytes used by each field. We will just read those many number of bytes and ignore them. That’s how we will reach to the start of next transaction (if any). After all the transactions are processed, we will be at the beginning of next block and the process repeats.

4.3 Genesis block Header

  1. We see that initial \(4\) bytes match F9 BE B4 D9, which corresponds to little endian of 0xD9B4BEF9. This is a match.
  2. Next \(4\) bytes read as 1D 01 00 00, which corresponds to little endian of 0x0000011D. This implies that block is spanning in more \(285\) bytes. This makes genesis block have storage space of \(285+8=293\) bytes. This means that first block is stored in offset \(0\)-\(292\) and next block starts at offset \(293\). We can confirm it by going to hexadecimal index 0x125 (which is equivalent to decimal of \(293\)) and reading the magic number. This process can be repeated to see that third block starts at hex offset 0x205 and so on..
  3. Next \(4\) bytes corresponds to version number which is specified as 01 00 00 00 which is little endian equivalent to \(1\).
  4. Next \(32\) bytes specify the previous block hash. This is specified as 0x00 repeated \(32\) times till hex index 0x2C.
  5. Next \(32\) bytes specify the merkle hash. These are 3B A3 ED FD 7A 7B 12 B2 7A C7 2C 3E 67 76 8F 61 7F C8 1B C3 88 8A 51 32 3A 9F B8 AA 4B 1E 5E 4A which is the little endian of 0x4A5E1E4BAAB89F3A32518A88C31BC87F618F76673E2CC77AB2127B7AFDEDA33B.
  6. Next \(4\) bytes refers to time. The value is 29 AB 5F 49 which is little endian of 0x495FAB29. Putting this value in online time converter gives the time as GMT: Saturday, January 3, 2009 6:15:05 PM.
  7. Next \(4\) bytes specify the nonce which is 0x1D00FFFF (after converting to big endian) - \(486604799\) in decimal.
  8. Next \(4\) bytes specify the difficulty as 0x7C2BAC1D (after converting to big endian) - \(2083236893\) in decimal.

4.4 C++ codes

First, we will print information about individual blocks by skipping over transactions. Later, we will read data about each transaction, compute size of individual size of each transaction and display the offsets.

4.4.1 Header summary

4.4.1.1 C++ Code for Header Summary

Here, we present the C++ code to show information about initial \(4\) blocks of Bitcoin (As initial \(1\)k data have \(4\) blocks only). The genesis block have index of \(0\).

#include <iostream>
#include <fstream>
#include <algorithm>
#include <string>
#define HEX( x, len ) std::setw(2 * len) << std::setfill('0') << std::hex << std::uppercase << (((1ll << (8 * len)) - 1) & (unsigned int)( x )) << std::dec

// Returns the file contents as C++ string
std::string get_file_contents(const char *filename)
{
    std::ifstream in(filename, std::ios::in | std::ios::binary);
    if (!in)
    {
        std::cerr << "Error in opening file" << std::endl;
        throw errno;
    }

    std::string contents;

    // Allocate required memory in heap for string
    in.seekg(0, std::ios::end);
    contents.resize(in.tellg());

    // Copy contents from file to string
    in.seekg(0, std::ios::beg);
    in.read(&contents[0], (int)contents.size());

    // return the string
    return contents;
}

struct BlockHeader
{

};

struct Block

int main(int argc, char** argv)

        memcpy(&block, contents.c_str() + offset, 88);

        std::cout << "Offsets of block #" << i << ": 0x" << HEX(offset, 4) << " to 0x" << HEX(offset + block.block_size + 8 - 1, 4) << std::endl;

4.4.1.2 Working

We can see that we have two structs in above code: BlockHeader and Block. BlockHeader consumes \(80\) bytes of space in memory, and it is enforced by choosing the data types of appropriate size so that no padding is there. We have Block with magic number and size as \(4\) bytes each, and block header just after them. Overall, we have no padding in the struct and blocks can be placed consecutively without wasting space. This allows us to use memcpy to copy bytes directly to struct without manually copying the bytes for individual fields. And people say python allows us to write small code…

Inside the main, we first read the file contents as binary file into a string. Then, we are printing the information about first \(3\) blocks of Bitcoin. We first copy \(88\) bytes from source file to a block, which completely fills all the fields of above block. Then, we print the information about them by iterating over each field, so there is nothing new here. One thing to note is that we are printing the hash in reverse order, and it is because we don’t have 256-bit data type in C++. We are manually printing it in big-endian format.

After printing information about block, we update our offset variable by 8 + block size to make it point to next block.

4.4.2.1 C++ code to read variable integer

Before going into actual code, we need to see how to work with variable integers. Since we are just reading the data, we will only consider the code to print the value. The reader is encouraged to write a code which takes an std::uint64_t as input and prints the corresponding hex value on screen. Why \(8\) byte integer? Good question. In the code, we just need to use integer, no matter how it is stored on actual storage. What data type should we choose in code to work with? Most practical choice will be to store everything in \(8\) byte integer and work with it. When we want to store it in Bitcoin storage, we can apply checks and write corresponding hex output.

Here is the code which reads from memory location str, and perform two things: reads the variable integer starting from str into \(8\) byte integer (no matter the actual bytes used in storage) and increment the delta value by corresponding amount of bytes from storage. Why are we increasing the delta instead of setting it to exact values? What is delta? We are using a trick and think about what will happen if we pass delta as offset and str as base address where byte \(0\) is stored + offset?

uint64_t read_varint(const char* str, size_t& delta)
{
    uint64_t output = 0;

    memcpy(&output, str, 1);
    if (output < 0xFD)
        delta += 1;
    else if (output == 0xFD)
        output = *(uint16_t*)(str + 1), delta += 3;
    else if (output == 0xFE)
        output = *(uint32_t*)(str + 1), delta += 5;
    else
        output = *(uint64_t*)(str + 1), delta += 9;

    return output;
}

        {
            std::cout << "\t\tTransaction #" << transaction_index << " offsets: 0x" << HEX(offset, 4) << " to 0x";

            // skip version number

            // read input
            auto n_inputs = read_varint(block_base + offset, offset);

            while (n_inputs--)
            {
                // skip previous transaction hash and output index
                offset += 36;

                // read signature script length
                auto script_len = read_varint(block_base + offset, offset);

                // skip script and sequence number
                offset += script_len + 4;
            }

            // read outputs
            auto n_outputs = read_varint(block_base + offset, offset);

            // read all outputs
            while (n_outputs--)
            {
                // skip Satoshis
                offset += 8;

                // read length of public key script
                auto script_len = read_varint(block_base + offset, offset);

                // skip key script
                offset += script_len;
            }

            // skip lock time
            offset += 4;

            std::cout << HEX(offset - 1, 4) << std::endl << std::endl;
        }
    }
}
